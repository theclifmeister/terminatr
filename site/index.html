One terminal for all your coding agents.
A coordinator you talk to, threads that do the work.

You talk to one coordinator. It splits the work into tasks and hands each to a thread: an agent in its own git worktree that pushes a branch and reports back. tm, a single binary, keeps every agent running in a background server when you close the terminal, and its dashboard shows what each one is doing and what waits for you. All progress lives in plain markdown under ~/.terminatr/projects/, so clearing an agent's context loses nothing.

01 What it does

  • ◆ One coordinator, many threads

    The coordinator is your single point of contact. It turns what you ask into tasks and starts a thread for each: an agent in its own git worktree and branch, so they never trip over each other. All progress lives in markdown under ~/.terminatr/projects/, so clearing an agent's context loses nothing.

  • ● Survives the terminal

    tm is a client; the agents live in a background server. Close the window, drop the SSH link, quit: they keep working. Run tm again from any terminal, at any size, and you are back. After a crash or an upgrade the server resumes them.

  • ▦ Dashboard, sidebar, popup

    Every session and project with its live state: working, blocked, idle. A project tree on the left of every screen, an info panel beside each agent, and a project popup (a) with its overview, inbox, tasks and settings. Filter the tree with /, jump to what needs you with w, and hover a glyph to see what it means. Keyboard first, mouse everywhere, the same view in every terminal you open.

  • ⎇ PRs, merged when CI is green

    Threads push their branch and the coordinator opens the pull request on GitHub or Azure DevOps. tm watches the checks: a failing run goes back to the thread with the log, a conflict with main asks for a merge. Threads can't merge; the coordinator does, once the checks pass.

  • ✓ Tasks and an inbox

    Tasks with steps in a plain TASKS.md: on deck, in motion, needs you, done. + adds one, from a template if you like. Threads hand in reports; the coordinator reads them from its inbox and moves the task. What waits for you, a review, a question, a red build, comes first under NEEDS YOU.

  • ⌁ Works over SSH

    It is a terminal program, so it goes where SSH goes. Copying from a pane lands on the clipboard of the machine you sit at (OSC 52). On a Mac the server starts in the desktop's session, so agents keep the keychain when you started it remotely. Remote Control picks up the coordinator from your phone.

  • ⇣ Homebrew, signed, self-updating

    One Go binary. macOS builds are signed with a Developer ID and notarised. Install with Homebrew or a one-line script; tm update upgrades it and tm doctor checks the setup.

  • ◈ Mods: make it yours

    Add a dashboard card, a sidebar column, a popup tab, a full view or a key, in TypeScript. Mods run sandboxed and ask before they get anything; the Tasks tab and the PR/CI column are mods too. More below.

  • ⚙ Agents as data

    Claude Code and Codex today; pi and opencode will follow. Agents plug in through a TOML manifest that says how to launch and resume them and read their state from hooks and session logs, not by scraping the screen. For Claude Code, tm's Agent mod (early access, off by default, Claude Code 2.1.289 or newer) adds a status band, a /tm pane and the session's context and token use.

03 Mods

Make tm yours. A mod is a folder with a mod.toml and, for code, a TypeScript file. It can add a card to the dashboard, a column to the sidebar, a tab to the project popup, a full view or a key. tm draws what it asks for, runs it in a sandbox, and keeps the actions to itself: a mod can offer to clear a session or answer a question, and tm asks you before anything runs.

Where a mod shows up

  • ▦ Views

    Dashboard cards, project popup tabs, full views with the header and sidebar kept in sight, and sections in the details and coordinator panels and in the sidebar, above or below the projects or under each one. tm owns the cursor, the scrolling and the filter.

  • ┃ Columns

    Cells in the sidebar and on the dashboard's rows: a context gauge, a CI mark, whatever a row should show.

  • ⌘ Commands

    A key on the dashboard, an entry in the ≡ menu, prefix plus that key inside any session, and tm mod run from a shell. A key tm already uses stays tm's.

  • ✉ Notifications

    OS notifications with buttons that run tm's own actions: answer an agent's question with one of its options, accept or send back a review, show the task. Each button opens tm's confirmation first.

  • ⚒ Agent tools

    Tools a mod offers your agents, served by tm mcp. The consent screen shows each tool's description and input in full, as the agent will read them.

  • ⛨ Guard rules

    Rules that refuse more of what agents may run, never less: a mod can tighten the guard, not loosen it. A change reaches running sessions at once.

  • ◇ Suggested defaults

    Values a mod suggests for everyday settings such as auto-close or PR follow-ups. They change nothing until you apply them (d in the Mods tab), and your own settings win. Safety settings are off limits.

  • ◐ Themes, keys, code hosts

    Data mods change the theme, icons, keymap and layout. A code host mod serves another forge: GitLab merge requests show and merge as tm's PRs do.

Safe by design

  • ✓ You consent first

    Installing shows what a mod asks for in plain words. It installs off; you turn it on in the Mods tab or with tm mod enable, for every project or only some. Install from the Mods tab too: i takes a folder or a git URL, and e installs an example.

  • ▣ Sandboxed

    Each code mod runs in its own host under the OS sandbox: seatbelt on macOS, landlock on Linux, a restricted token on Windows. It reads its own files and nothing else, starts no program and, on macOS and Linux, makes no connection; it asks tm, which checks its grants.

  • ⏎ Mods draw, tm acts

    A row or a button only names an action: clear a session, answer a question, accept a task. tm checks it against the live state, asks you, then runs it. Clearing starts the agent on a fresh conversation once it is idle; the project's files keep its state.

  • ⌂ Only you act as you

    Your console talks to the server on a socket of its own that agents' sandboxes don't allow, so a thread can't open your views, press your buttons or clear a session in your name. If a mod gets in the way, tm --no-mods starts with the built-in ones only.

Built in

Some of tm is mods already, drawn the same way yours are: the project popup's Tasks tab, the sidebar's PR/CI column, the Memory tab, the default task templates, and the default theme, icons, keymap, layout and guard policy. The Tasks tab, PR/CI column and Memory tab are in the examples too: to change one, copy it under another id, install the copy and turn the built-in one off.

Try one

git clone https://github.com/theclifmeister/terminatr
tm mod install https://github.com/theclifmeister/terminatr/tree/v0.43.0/examples/mods/standup

Then turn it on in the Mods tab (, then 3) or with tm mod enable standup. Or skip the shell: in the Mods tab, e lists the examples and i installs the selected one. tm mod install also takes a folder, a git URL or a repository's subfolder (<git-url>//<folder>@<tag>). The examples have one of each kind.

Write your own

tm mod new my-mod --kind column
tm mod dev my-mod
tm mod test my-mod
tm mod logs my-mod

new writes a scaffold with the types and a test fixture (--kind also takes hook, theme, icons, keymap and rules). dev runs it live and restarts it on each save, test replays its fixtures, logs shows what it printed.

04 Servers working together

Pair your tm server with a colleague's, or with your own on another machine. Both dial out to a relay you run, so neither machine needs an open port. A paired server sees the projects you choose to share, can watch or type into their agents' panes if you let it, and its coordinator can write to yours once you both link the projects.

  • ⇄ Pair with a code

    tm peer pair on one server shows a one-time code; tm peer join takes it on the other. Both then show the same six digits to compare before either says yes. Each server pins the other's key, so nobody can step in later, the relay included.

  • ◉ Share a project

    Pairing alone shows nothing. Turn on Shared with paired servers for a project and it appears in the other server's sidebar: its dashboard, what waits for you, inbox, threads and tasks. Never its files, settings, repos or worktrees.

  • ▢ Remote panes

    Let a paired server view or write to the panes of what you share, and it opens your coordinator or a thread in its own console, as if it ran there. You decide on your side; off is the default. While the link is down the pane keeps its last screen.

  • ✉ Coordinators that talk

    Link a project to one on the other server and the two coordinators can write to each other. Ask from tm instead of explaining what to type: the other user sees the link request under NEEDS YOU and accepts or declines it. Each message waits for your OK unless you say otherwise.

Pair two servers

Once, each of you in your own terminal, or in the settings' Peers tab (, then 4): n shows a code, j takes one.

On one server

tm peer pair --relay relay.example.net --as mini

Prints a code like relay.example.net/7Q4M-K2XD-9HVA-PT3C. It works once, for 10 minutes. Pass it on yourself, in a chat or a call; the relay never sees it.

On the other

tm peer join relay.example.net/7Q4M-K2XD-9HVA-PT3C --as studio

Both terminals show Check: 418 207. Answer y on both sides only when the digits match; different digits mean someone is in between.

Link two projects

tm project link acme mini/api --request

Sets your side and asks mini's user to link back. They accept or decline it there, in api's Messages tab; the answer comes back to your inbox. Or link from the project's Settings tab, under Linked projects.

Let it see your panes

tm peer panes studio write

view lets studio watch without typing, off shows nothing. There, tm attach mini/s-41 or the sidebar's mini group opens one.

Run your own relay

The relay is tm relay serve, from the same binary, on a host both servers reach: a small VPS, or a NAS at home. It stores nothing and only copies an encrypted stream between the two servers. It can see which servers connect and when, never names, projects, messages or panes. A bad relay can cut your link; it can't read it, change it or pair a stranger in.

A Linux VPS with a domain

sudo ~/.local/bin/tm relay install --domain relay.example.net

Point the name at the host and open port 443. It installs a sandboxed systemd service, gets its own Let's Encrypt certificate and renews it, updates itself daily, and ends with the tm peer pair line to use.

An IP address no domain

sudo ~/.local/bin/tm relay install --ip 203.0.113.5

For a public IP, a home server on your LAN or a tailnet address. The relay makes its own key and a self-signed certificate; servers check it by that key's pin, carried in its address (wss://203.0.113.5#sha256=…) and in the pairing code, so nobody types it.

Docker VPS or NAS

curl -fLO https://github.com/theclifmeister/terminatr/releases/latest/download/tm-relay-docker.tar.gz
tar xzf tm-relay-docker.tar.gz && cd tm-relay-docker

The image is ghcr.io/theclifmeister/tm-relay, for amd64 and arm64, running as a non-root user. The folder has three compose files: compose.selfsigned.yaml for an IP address, compose.acme.yaml with Caddy getting the certificate, and compose.yaml for certificate files you already have.

On a NAS port 8443

mkdir state && sudo chown 65532:65532 state
echo RELAY_IP=192.168.1.20 > .env
docker compose -f compose.selfsigned.yaml up -d

Runs on 8443, so the NAS keeps its own 443; docker compose -f compose.selfsigned.yaml logs relay shows the address to pair with, wss://192.168.1.20:8443#sha256=…. Back up state/: it holds the key. Where the folder is your own user's (Synology's File Station), skip the chown and add RELAY_USER=uid:gid to .env. Synology Container Manager, QNAP Container Station, Unraid and TrueNAS can run the same file as a project.

The operations guide has the rest: certbot or your own reverse proxy, limits, upgrades, and what each server's link status means.

05 Install

macOS 13+, Linux (glibc 2.28+) or Windows, with Claude Code or Codex. Pick your system.

Linux or macOS

curl -fsSL https://github.com/theclifmeister/terminatr/releases/latest/download/install.sh | sh

Installs tm into ~/.local/bin and checks the download's sha256.

Windows PowerShell

irm https://github.com/theclifmeister/terminatr/releases/latest/download/install.ps1 | iex

No admin rights needed. Windows support is early.

macOS or Linux, Homebrew

brew tap theclifmeister/terminatr https://github.com/theclifmeister/terminatr
brew trust theclifmeister/terminatr
brew install terminatr

Newer Homebrew wants you to trust a tap's formula once.

Then

tm

Then press n for a new project and enter to start its coordinator. Ctrl+B d brings you back to the dashboard, ? lists every key. The README has the same commands. Running Codex? Using Codex covers the setup.
